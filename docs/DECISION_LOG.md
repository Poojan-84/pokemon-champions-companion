# Decision Log

Every significant architectural or product decision gets recorded here, permanently. Never delete entries — if a decision is reversed, add a new entry noting the change and why.

---

## 2026-07-31 — Framework: Next.js
**Decision:** Use Next.js (App Router, TypeScript) as the core web framework.
**Reason:** SEO is the top stated priority. Next.js gives server-side rendering / static generation out of the box, which is required for competitive discoverability. It also has the largest React ecosystem, best AI-tooling support, and scales cleanly from a static content site (Phase 1) to an interactive app (Phase 2–3) without a rewrite.
**Alternatives considered:**
- Plain HTML/CSS/JS — rejected: no component reuse, no SEO tooling, doesn't scale to Phase 2/3 tools.
- WordPress — rejected: strong for pure content, weak once we need interactive team builder/calculator tools.
- Create React App (SPA) — rejected: poor default SEO, directly conflicts with top priority.
**Tradeoffs:** Slightly more setup/learning curve than plain HTML, but this is absorbed by AI-assisted development and pays off immediately at Phase 2.

## 2026-07-31 — Styling: Tailwind CSS
**Decision:** Use Tailwind CSS for all styling.
**Reason:** Fast to build and iterate with, keeps design consistent without a separate design system to maintain, and AI tools (Claude Code) generate high-quality Tailwind output reliably.
**Alternatives considered:** Plain CSS/SCSS (rejected — slower iteration, easier to end up inconsistent), CSS-in-JS libraries (rejected — extra dependency, no clear benefit for our use case).
**Tradeoffs:** Utility-class HTML can look verbose; acceptable tradeoff for iteration speed.

## 2026-07-31 — Content storage: Markdown/JSON in repo (no database yet)
**Decision:** Phase 1–2 content (Pokémon data, guides, tier lists, regulations) lives as structured Markdown/JSON files in the Git repository, not in a database.
**Reason:** No user accounts or dynamic user-generated content exist yet. A database adds hosting cost, complexity, and a new failure surface for zero benefit at this stage. Content-as-code is also easy for both of us (and Claude Code) to edit directly.
**Alternatives considered:** Headless CMS (Sanity/Contentful) — rejected for now, adds cost/complexity before it's needed; can be introduced later without much friction if editing becomes painful. A SQL database — rejected, premature until Phase 3 (user accounts).
**Tradeoffs:** Content updates require a Git commit + deploy rather than a CMS UI. Acceptable while we're a solo founder; revisit if update frequency becomes a bottleneck.

## 2026-07-31 — Hosting: Vercel
**Decision:** Deploy on Vercel.
**Reason:** Built by the Next.js team (best compatibility), zero-config GitHub-connected deploys, generous free tier, automatic preview URLs per change.
**Alternatives considered:** Netlify (comparable, but Vercel has tighter Next.js integration), self-managed VPS (rejected — unnecessary DevOps burden for a solo founder).
**Tradeoffs:** Vendor lock-in to Vercel's platform conventions; acceptable given the benefits and how portable Next.js code remains regardless.

## 2026-07-31 — Data sourcing: PokeAPI + hand-curated competitive data
**Decision:** Base Pokémon data (species info, base stats, types, abilities, sprites, etc.) is sourced from PokeAPI. Competitive-specific data — regulation legality, tier placement, role, common moves/items — is hand-curated by us. No automated usage-stat scraping in Phase 1.
**Reason:** PokeAPI is free, comprehensive, and well-maintained for base game data, so there's no reason to re-derive or hand-enter it. But "what's actually good in Champions right now" (tiering, legality, common sets) is a judgment call that reflects real competitive knowledge and our own editorial voice — the thing that differentiates this site (see VISION.md's "simplicity as a moat"). Scraping usage stats automatically would tie us to third-party sources of uncertain reliability/licensing before we've validated we even need that granularity.
**Alternatives considered:**
- Hand-entering all data (base + competitive) — rejected: duplicates work PokeAPI already does well, slower to keep base data current across game updates.
- Automated usage-stat scraping from a stats site — rejected for Phase 1: adds a fragile external dependency and legal/licensing uncertainty before the core content model is proven. Revisit as a possible Phase 2/3 enhancement once curated content ships.
**Tradeoffs:** Competitive fields require ongoing manual upkeep as the meta shifts — acceptable while solo-founder content volume is small; revisit if update cadence becomes a bottleneck (same risk noted in ARCHITECTURE.md).

## 2026-08-01 — SEO fundamentals pass: sitemap, robots.txt, structured data, meta audit, internal linking, canonicals
**Decision:** Ship a full SEO fundamentals pass across all three page types (homepage, /pokedex index, /pokedex/[id] detail, /tier-list) rather than adding SEO plumbing incrementally per feature: a generated sitemap.xml and robots.txt, JSON-LD structured data, an audit of every page's title/meta description, cross-links between the page types, and canonical URLs on every page.
**Reason:** SEO is priority #1 (CLAUDE.md), but it's the kind of work that's easy to defer indefinitely because no single page "needs" it to function — the payoff only shows up in aggregate, once a crawler actually indexes the site. Doing it as one deliberate pass once the core content types (Pokédex, Tier List) existed meant we could get the structure right once instead of retrofitting it three separate times. Specific calls made within the pass:
- **Sitemap + robots.txt** use Next.js's built-in `app/sitemap.ts` / `app/robots.ts` conventions, generated from the same `content/pokemon/*.json` files the pages themselves read — so new Pokémon entries automatically appear in the sitemap with zero extra maintenance, and the sitemap can never drift out of sync with what actually exists.
- **JSON-LD structured data**: schema.org has no dedicated type for a game creature/character — forcing one onto `Person` or `Product` would be technically parseable but semantically dishonest, and could plausibly cause Google to misclassify the content. We used `Thing` (the honest closest fit) for detail pages and `ItemList` for the Pokédex index and Tier List, since those two pages genuinely *are* lists of items — the schema fits the actual content instead of being bolted on. We deliberately did **not** add `sameAs` links to external wiki pages (e.g. Bulbapedia): building those URLs from our Pokémon names/ids would mean guessing at slugs we can't verify, and several of our entries are form variants (Floette-Eternal, Basculegion's male form) where the real wiki URL doesn't follow the obvious pattern. A missing `sameAs` costs us a small amount of entity-linking value; a broken or wrong one actively damages trust and could mislead both users and crawlers — not a trade worth making.
- **Meta description audit** surfaced that the detail pages' description was reusing the on-page summary text verbatim, which never names the Pokémon (correct in-page, since the name is already the heading right above it) but is wrong for a meta description, which search results display with zero surrounding context. Descriptions were rewritten to explicitly include the Pokémon's name, tier, and top moves.
- **Internal cross-linking**: before this pass, the three page types only connected to each other through the site-wide nav — no in-content links existed between a Pokémon's detail page and the Tier List, for instance. Per ARCHITECTURE.md's topical-cluster strategy, contextual in-content links (not just chrome) are what build internal linking equity, so we added them where they were a natural fit (tier badge → Tier List, breadcrumb → Pokédex, a one-line cross-link on each index page) rather than everywhere possible.
- **Canonical URLs**: added on every page via `metadataBase` + `alternates.canonical`, to remove any ambiguity for crawlers if the same content ever becomes reachable via more than one URL shape.
**Alternatives considered:**
- Skipping JSON-LD until a more specific/official vocabulary exists — rejected: `Thing`/`ItemList` are valid, honest, and add value now; waiting indefinitely for a "Pokémon" schema.org type that will likely never exist isn't a real plan.
- Guessing external wiki URLs for `sameAs` — rejected: see reasoning above; a wrong URL is worse than no URL.
- Doing SEO piecemeal (e.g. only on new pages going forward) — rejected: would leave already-shipped pages (Pokédex, Tier List) permanently under-optimized and require a second pass later anyway.
**Tradeoffs:** The sitemap's `lastModified` is a build-time timestamp rather than derived from actual content-file change dates, so it doesn't perfectly reflect real content freshness — acceptable for now given our small, infrequently-changing content set; revisit if we need more precise freshness signals later.

## 2026-08-01 — Markdown content pipeline: gray-matter + marked + Tailwind typography
**Decision:** Guides (`/content/guides/*.md`) use `gray-matter` to parse YAML frontmatter and `marked` to render the Markdown body to HTML. The rendered HTML is styled with Tailwind's official `@tailwindcss/typography` plugin (`prose` classes) rather than hand-written CSS.
**Reason:** The guides system only needs two things: pull frontmatter fields (title, description, dates) out of a file, and turn Markdown body text into HTML. `gray-matter` and `marked` each do exactly one of those jobs, are small and well-maintained, and require no configuration. The alternative — `remark`/`unified` — is the more common choice for advanced Markdown pipelines, but it's a full plugin-based transform ecosystem (parser + multiple plugins + a serializer) built for cases where you need to programmatically manipulate the Markdown AST (custom components, MDX, rehype plugins, etc.). We don't do any of that here, so it would be meaningfully more dependencies and API surface for the same end result. `@tailwindcss/typography` avoids hand-rolling heading/paragraph/list spacing and color rules — it's the same "boring technology" reasoning as choosing Tailwind itself (see the Tailwind CSS entry above): official, well-documented, and one less thing to maintain by hand.
**Alternatives considered:**
- `remark` + `remark-html` (+ possibly `rehype-sanitize`) — rejected: more dependencies and a heavier mental model (AST transforms) for a need that's just "frontmatter + HTML," not custom Markdown extensions.
- Hand-rolled CSS for guide content — rejected: `@tailwindcss/typography` is actively maintained by the Tailwind team, covers the full set of Markdown-generated elements (headings, lists, blockquotes, code, etc.) correctly out of the box, and is one line to enable (`@plugin "@tailwindcss/typography";`).
- HTML sanitization library (e.g. `sanitize-html`, `rehype-sanitize`) for the rendered output — not added: all guide Markdown is authored by us directly in the repo (not user-submitted), so there's no untrusted-input risk that would justify the extra dependency. Revisit immediately if guides ever accept external/community-submitted content.
**Tradeoffs:** `marked`'s output is plain HTML with no built-in AST for programmatic manipulation — if we ever need custom rendering per element (e.g. auto-linking Pokémon names mentioned in guide text), we'd likely need to switch to `remark`/`rehype` then. Acceptable now since guide content is simple prose; revisit if guide content needs grow more structured.

## 2026-08-01 — Mobile/performance QA pass: contrast, touch targets, nav wrapping
**Decision:** Run a dedicated mobile/performance QA pass across all page types (375px/768px/1440px viewports + Lighthouse against a production build) rather than treating "it looked fine when I built it" as sufficient, and fix everything the pass turned up rather than deferring any of it.
**Reason:** Individual feature work had been visually checked page-by-page as it shipped, but nothing had systematically tested color contrast ratios or touch-target sizes against real accessibility thresholds, and nothing had re-verified the nav after each new link was added to it. The pass found real, objective defects, not style preferences:
- **10 of 23 type/tier badge color combinations failed WCAG AA contrast** (4.5:1 for normal text) — e.g. white text on `orange-500`/`green-500`/`purple-500` only reached 2.2–4.1:1. Lighthouse's automated audit only samples what's rendered on the page it's given, so it caught just one instance (`Ground` on Garchomp's page); testing all 23 combinations programmatically (via a canvas-based contrast check against the live rendered colors, since Tailwind v4 renders colors in `lab()`/`oklch()` rather than plain `rgb()`) surfaced the other 9. Fixed by darkening backgrounds or switching to dark text within the same color family per badge — no new colors introduced, no visual redesign.
- **Several touch targets measured under 24px tall** (nav links, the search input, breadcrumbs, cross-link sentences) — these were sized to their text content alone because their parent flex containers used `items-center`, which sizes children to content rather than stretching them to the row height. Fixed by padding each element directly rather than relying on the row's padding.
- **A nav-wrapping bug found as a side effect of the touch-target fix, not by the original checks**: "Tier List" was silently breaking onto two lines at 375px once three nav links plus the "Champions Companion" wordmark didn't fit on one row. This had been invisible to every prior QA step because those checks only tested `document.documentElement.scrollWidth > clientWidth` (page-level horizontal overflow) — the wrapped text stayed within the viewport, so it never triggered an overflow flag despite looking visibly broken. Fixed with `flex-wrap` on the nav link group (so the group drops to its own row instead of breaking mid-phrase) plus `whitespace-nowrap` per link.
- **Inline links inside guide-body prose (~18px tall) were deliberately left alone** — WCAG 2.5.8 Target Size explicitly exempts links embedded in a sentence, since you can't make every word-link 24px tall without breaking text flow.
**Alternatives considered:**
- Trusting Lighthouse's single-page contrast audit as sufficient — rejected: it only evaluates colors actually rendered on the page under test, and our badge colors are keyed by Pokémon type/tier, so most combinations never appear on any one sampled page. A systemic check across every defined combination was needed to catch the rest.
- Checking only for horizontal page overflow as the layout-correctness signal — rejected going forward: this pass is the proof that overflow alone misses wrapping bugs that occur entirely within the viewport. Future layout QA should also check for unexpected multi-line wraps on single-line UI elements (nav links, buttons, badges), not just overflow.
**Tradeoffs:** None of substance — these were bug fixes, not new tradeoffs. The one thing worth naming: because badge colors are shared across every page that renders a Pokémon (Pokédex, Tier List, Search, detail pages), any future new type/tier color must be contrast-checked before shipping, not assumed safe by analogy to existing ones.

Verified via Lighthouse against a production build after fixes: Accessibility is 100 on all 6 page types (Pokémon detail pages were 96 before the contrast fix); Performance/Best Practices/SEO all 95–100.

## 2026-08-01 — Team Builder v1: scope boundaries
**Decision:** Team Builder v1 (`/team-builder`) is intentionally scoped down in three ways rather than trying to be a complete tool on first ship: it persists to browser `localStorage` only (no accounts, no cross-device sync), it only lets you pick from our current 20 curated Pokémon, and item/move selection per Pokémon is restricted to that Pokémon's pre-curated `commonItems`/`commonMoves` rather than a full items/moves database.
**Reason:** Each of these is a deliberate "don't build the bigger thing yet" call, not an oversight:
- **localStorage, not accounts** — user accounts and saved-team sync are explicitly Phase 3 scope (see ARCHITECTURE.md's Database row and PRD.md). Building account infrastructure just to persist one team would mean standing up a database and auth before either is otherwise needed — exactly the premature-complexity trap ARCHITECTURE.md's principle 1 warns against. `localStorage` gives real persistence (survives reloads) at zero infrastructure cost, which is enough for v1.
- **20-Pokémon picker, not the full Pokédex** — the picker is bounded by whatever `getAllPokemon()` returns, so it grows automatically as the database expands; no separate work is needed later, but v1 ships honestly scoped to what's actually curated today (with an explicit in-UI note: "Building from our current 20-Pokémon database — more coming soon").
- **Curated items/moves only, not a full items database** — we don't have a general items/moves database (see the 2026-07-31 "Data sourcing" entry — competitive fields are hand-curated per Pokémon, not sourced from a general game-data API). Letting users assign an arbitrary item/move not on a Pokémon's curated list would mean either building that general database now (out of scope for v1) or allowing legal-but-unvetted combinations we have no data backing.
**Also notable:** `lib/typeChart.ts` (the 18×18 type effectiveness chart) is built as standalone, reusable game-mechanics data — not Team Builder-specific. It's already used by `lib/teamTypeCoverage.ts` here, and is the same data a future type coverage checker or matchup pages feature (both already listed in ROADMAP.md's Phase 2 planning) would need — no rework required to reuse it.
**Alternatives considered:**
- Standing up Supabase/accounts now to support "real" persistence — rejected: pulls Phase 3 infrastructure forward for a v1 feature; `localStorage` is sufficient and reversible (swapping in real sync later doesn't require redesigning the team-builder UI, just the persistence layer).
- Allowing free-text item/move entry — rejected: would let users build teams referencing items/moves we have no curated data for, undermining the "curated, trustworthy" positioning from VISION.md.
**Tradeoffs:** A team built on one device/browser doesn't follow the user anywhere else, and clearing browser data loses it — acceptable for v1 given no accounts exist yet to sync to regardless. Revisit once Phase 3 accounts ship.

## 2026-08-01 — Type Coverage Checker: offensive counterpart to Team Builder, not an extension of it
**Decision:** Type Coverage Checker (`/type-coverage`) reuses Team Builder's search/select picker UI (same slot-grid pattern, same component shape) but is built as its own standalone component (`components/TypeCoverageChecker.tsx`) and lib function (`lib/offensiveTypeCoverage.ts`), not as a mode toggle inside Team Builder or a reuse of `lib/teamTypeCoverage.ts`. It also has no `localStorage` persistence and applies none of `lib/teamValidation.ts`'s Regulation M-B rules (species clause, duplicate items, one Mega Stone max).
**Reason:**
- **Offensive vs. defensive are different questions, not variations on one** — `lib/teamTypeCoverage.ts` answers "what is my team weak/resistant/immune to" (defending types of the selected Pokémon vs. all 18 attacking types). This tool answers the inverse: "what do my selected Pokémon's *moves* hit super-effectively" (attacking types derived from `commonMoves` vs. all 18 defending types). Bolting a second mode onto `TeamBuilder.tsx` would have coupled two genuinely different mental models (defense vs. offense) behind one piece of state, and reusing `teamTypeCoverage.ts` directly wasn't possible since it's keyed on defending types, not move types — so a new lib function was the honest fit, not a shortcut.
- **No persistence** — unlike a team you're building to actually use, a coverage check is a quick, disposable question ("do these 6 hit hard enough?"), not something you'd expect to survive a reload. Skipping `localStorage` here isn't a scope-down under pressure, it's that nothing asked for persistence in the first place — adding it would be building a feature nobody requested.
- **No Regulation M-B rule checks** — those rules (one of each species, no duplicate items, one Mega Stone) are Team Builder's job because they only matter when you're assembling a *legal team to play*. This tool answers a narrower question about move coverage and doesn't care whether the 6 Pokémon you picked could legally battle together — you might deliberately select 6 Pokémon that share a type just to see how thin the coverage gets.
- **Move type data comes from `lib/moveIcons.ts`, not a new source** — `moveIcons.ts` already curates each move's type (for icon tinting), so a new `getMoveType()` export reuses that data instead of re-deriving or duplicating it; status moves (Protect, Trick Room, etc.) return `null` and are excluded from the coverage calculation since they have no attacking type.
**Also notable:** Fixed a copy staleness bug found while building this: both Team Builder's and this tool's "Building from our current N-Pokémon database" line now read `pokemon.length` instead of a hardcoded `"20"` — the count had already drifted to 22 after the Tyranitar/Excadrill addition earlier the same day.
**Alternatives considered:**
- A toggle inside Team Builder ("defensive" vs. "offensive" view of the same selected team) — rejected: conflates two different jobs (build a legal team vs. check offensive coverage of any 6 Pokémon) behind one piece of state, and would force Regulation M-B rules onto a tool where they don't apply.
- Showing all three categories (super-effective / resisted / no-effect) per type in the UI — computed internally (`OffensiveCoverageEntry` has all three counts, useful for verification) but only two are surfaced ("Super effective against" / "No coverage against"), since "resisted" and "neutral" both amount to the same actionable answer — that type isn't covered — and a three-way breakdown would be closer to a raw matrix dump than the plain-language summary VISION.md's 30-second rule calls for.
**Tradeoffs:** None of substance — this is additive, reusing existing verified UI/data patterns (picker, `TypeBadge`, `typeChart.ts`) rather than introducing anything new architecturally.

## 2026-08-02 — Rental Team Directory v1: data model + single-placeholder scope
**Decision:** Rental Team Directory v1 (`/rental-teams`) follows the same content-as-data pattern as `content/pokemon/*.json`: each core or full team is one hand-authored JSON file in `content/rental-teams/`, read via a new `lib/rentalTeams.ts` (`getAllRentalTeams()`, mirroring `lib/pokemon.ts`'s `getAllPokemon()`). It ships with **exactly one placeholder entry** (`placeholder-example.json`, clearly labeled as such in both its `name` and `summary` fields) rather than any real curated teams.
**Reason:**
- **Content-as-data, not a new mechanism** — this is the same pattern as the 2026-07-31 "Content storage" and "Data sourcing" entries: no database, no automated scraping, hand-curated JSON in Git. Rental teams have no PokeAPI equivalent (there's no "base data" half to auto-fetch — every field here is a curation call), so unlike `content/pokemon/*.json` there's no generator script; every entry is written by hand from the start.
- **Load-time validation, not silent failure** — `lib/rentalTeams.ts` validates every entry's `pokemonIds` against `getAllPokemonIds()` and its `type` against the `"core" | "full-team"` enum, throwing a clear error (naming the file and the bad value) rather than letting a typo silently drop a Pokémon from a card or vanish an entry from both directory sections. Verified by temporarily feeding it a bad Pokémon id and a bad `type` value — both failed the build loudly with a clear message, as intended, before being reverted.
- **One placeholder entry, not zero and not fabricated real data** — shipping with zero entries would make both directory sections show empty "check back soon" states with no way to verify the card layout renders correctly; inventing plausible-looking "real" entries would risk being mistaken for actual curated guidance, undermining the "curated, trustworthy" positioning from VISION.md (the same reasoning as Team Builder v1's item/move scoping). A single, unmistakably-labeled placeholder (`"PLACEHOLDER — replace with real curated data"` as the name, a summary that says outright not to treat it as real guidance, `"PLACEHOLDER"` as the source note) gives the UI something real to render and QA against without pretending to be finished content. A page-level banner reinforces this same message so it's not only visible in the fine print of one card.
- **Archetype linking via guide heading anchors, not a separate archetype registry** — the optional `archetype` field stores a kebab-case slug (e.g. `"sand-offense"`) that must match a heading in `content/guides/team-archetypes.md`. Rather than inventing a second source of truth for archetype names, `app/guides/[slug]/page.tsx` now assigns each `<h2>` an `id` derived from its own heading text via a new `slugifyHeading()` (`lib/guideIcons.tsx`), so the two pages stay linked through the guide's actual content instead of a hand-maintained mapping that could drift out of sync.
- **No per-card "core" vs. "full-team" badge** — the two page sections (headed "Cores" and "Full Teams") already communicate which type an entry is; a redundant per-card tag would repeat information the section heading already gives, and per VISION.md's 30-second rule, data shouldn't be shown just because it exists. This also meant no new badge color needed introducing or contrast-checking — the one new UI element that does need a color (the archetype badge) reuses the existing `accent` on `bg-surface` pair, already documented in `globals.css` at 11.85:1, well clear of WCAG AA.
**Alternatives considered:**
- Zero seed entries — rejected: leaves both sections permanently empty until real content lands, no way to visually verify the card component actually works.
- Fabricated "realistic" example entries instead of an obvious placeholder — rejected: risks being mistaken for real competitive guidance, the exact trust problem VISION.md's "simplicity as a moat" positioning is meant to avoid.
- A hand-maintained archetype name/slug lookup table instead of anchor ids derived from actual heading text — rejected: a second source of truth that could silently drift from the guide's real headings; deriving the id from the heading text itself means they can't disagree.
- A visible "core"/"full-team" badge per card — rejected: redundant with the section heading it would sit inside, and would have required a new contrast-checked color for no informational gain.
**Tradeoffs:** The directory currently has no real informational value beyond demonstrating the page works — that's the intended state of a v1 seed, not an oversight, but it means `/rental-teams` shouldn't be promoted (SEO-wise or otherwise) as if it had real content yet. Tracked as an explicit backlog item (BACKLOG.md) to replace the placeholder with curated tournament-sourced teams.

- Silently including the Sinistcha + Farigiraf core with a `sourceNote` written to sound equally stat-backed as the others — rejected: dishonest by omission, the exact trust risk this directory exists to avoid.

Rain and a second Sand Offense full team remain open (tracked in BACKLOG.md) until a verified real roster fitting our curated Pokémon is found.

## 2026-08-02 — Speed Calculator v1: simplified nature selector, ability-modifier exclusion, Trick Room as sort direction
**Decision:** Speed Calculator (`/speed-calculator`) implements the full Level 50 VGC speed formula in a pure, unit-testable `lib/speedCalc.ts` (no React), but makes three deliberate simplifications/exclusions rather than modeling every real-game mechanic: a 3-way nature selector instead of the full 25-nature list, no ability-based speed modifiers (Sand Rush, Swift Swim, Chlorophyll, Unburden, etc.), and Trick Room modeled purely as a display-layer sort-direction flip rather than a stat multiplier.
**Reason:**
- **3-way nature selector ("Boosts Speed" / "Neutral" / "Lowers Speed"), not a 25-nature dropdown** — every one of the 25 natures affects Speed in exactly one of three ways (+10%, unchanged, -10%), so a full nature dropdown would force a beginner to know which of 25 named natures (Timid? Jolly? Hasty? Naive?) maps to which Speed effect, when the only fact that actually matters for this calculator is the Speed direction itself. This is the same reasoning as VISION.md's 30-second rule and the Type Coverage Checker's two-group summary (see that DECISION_LOG.md entry) — showing the underlying mechanic in its simplest correct form beats a complete-but-intimidating picker. The math applied is identical to a real nature's ±10% Speed modifier; nothing is approximated, only the *selector* is simplified.
- **Ability-based speed modifiers explicitly out of scope, flagged rather than silently wrong** — Sand Rush, Swift Swim, Chlorophyll, Unburden, and similar abilities can double (or more) a Pokémon's effective Speed under specific field/item conditions this calculator doesn't track (weather, HP thresholds, item removal timing). Modeling them correctly would require also modeling weather/terrain state, which is real scope creep beyond "given these stats, what's the Speed stat" — a materially bigger v2. Rather than silently omit them and let a Sand Rush Excadrill look artificially slow with no explanation (actively misleading, the same class of problem as the Rental Team Directory's stale-banner and wrong-`sameAs`-link precedents), `lib/speedCalc.ts` exports `hasUnmodeledSpeedAbility()`, checked against each selected Pokémon's real curated `abilities` array (not hardcoded per Pokémon id), and the UI shows an explicit inline note — "Ability-based speed boosts (e.g. Sand Rush) not yet factored in" — on both that Pokémon's config card and its Turn Order row. Checking the actual ability list (rather than a hardcoded per-Pokémon-id exception) means the check stays correct automatically as the Pokémon database grows, with no separate maintenance step.
- **Trick Room modeled as sort direction, not a stat multiplier** — Trick Room does not change any Pokémon's Speed stat in the real games; it inverts which end of the Speed ordering moves first. Multiplying Speed by some Trick Room "modifier" would be mechanically wrong (and would corrupt the displayed Speed number itself). `calculateSpeed()` has no Trick Room parameter at all; the Trick Room toggle only feeds `rankBySpeed()`, a separate pure sort function that flips comparison direction. This keeps "what is this Pokémon's Speed stat" (a fact) cleanly separate from "who moves first" (a function of that fact plus the active field condition) — the same kind of separation of concerns as keeping `lib/teamTypeCoverage.ts` (defensive) and `lib/offensiveTypeCoverage.ts` (offensive) as distinct functions rather than one conflated calculation.
- **Combined-multiplier truncation, not per-step flooring** — item, paralysis, and Tailwind multipliers are combined into one product and truncated once at the end, not floored after each individual step, because that's how the real games stack simultaneous stat modifiers (per Bulbapedia's stat-modifier mechanics: multiple active modifiers on the same stat combine their numerators/denominators before one truncation). The two approaches can disagree — e.g. a Choice Scarf + paralysis + Tailwind Pokémon with a post-nature stat of 101 computes 151 with combined-then-floor but only 150 if floored after each step — so this was a real accuracy decision, not a stylistic one, verified against this exact example in code comments and confirmed via a real in-browser calculation (Timid 252 SpA Garchomp: 169 base, 253 with Scarf, 126 with Scarf + paralysis, matching known reference values).
**Alternatives considered:**
- A full 25-nature dropdown — rejected: adds a memorization burden (which named nature does what to Speed) for zero mechanical gain over a 3-way selector, since Speed only has three possible nature outcomes.
- Silently omitting the ability caveat — rejected: an incomplete number presented as complete is worse than an honest gap, per the same reasoning used for the Rental Team Directory's Rain/Sand-Offense gap and stale-banner decisions.
- Hardcoding the ability caveat per specific Pokémon id (e.g. `if (id === "excadrill")`) — rejected: doesn't scale, and silently stops being correct the moment a new Sand Rush/Swift Swim Pokémon is added without a matching code change; checking the real `abilities` array is self-maintaining.
- Giving Trick Room its own multiplier field in `SpeedCalcInput` — rejected: would be mechanically incorrect (Trick Room doesn't touch the stat) and would blur the calculator's most important distinction for a beginner to understand: stat vs. turn order.
**Tradeoffs:** Speed ties are broken by preserving each Pokémon's original selection order rather than modeling the real game's coin-flip tiebreak — acceptable for v1 since exact tie-break outcomes are non-deterministic in-game anyway and not the primary question this tool answers. Weather/terrain-conditional abilities remain a known, clearly-flagged gap until a future version scopes in field-state tracking.
